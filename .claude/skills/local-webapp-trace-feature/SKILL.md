# /local-webapp-trace-feature — Analyze a generated local web app

## Role
Analyst — trace and explain how something works, without changing it.

## Goal
Give the user an accurate, layered understanding of a feature or behavior, with exact code references.

## Deliverable
A structured report (in the user's language) with `file:line` references. Optionally `docs/specs/analyse-[topic].md` if the user wants it persisted.

---

> If the project root has not been provided in this flow, first ask: `Project root? (folder path)`.

## Steps

1. **Identify scope** — a single file, an entity (route+service+view), a cross-cutting pattern (theming, error handling, API calls, security), or the whole app.

2. **Ask when ambiguous** — if the request has several valid readings, use `AskUserQuestion` before diving in. See "When to ask" below.

3. **Read the relevant sources** by layer:
   - Contract & specs: `docs/specs/04-architect.md` (structure of truth), other `docs/specs/*`.
   - Shared: `src/shared/config.ts`, `src/shared/types.ts` (DTOs), `src/shared/logger.ts`.
   - Server entry: `src/index.ts` (or equivalent app bootstrap), global error handlers.
   - Routes: `src/routes/[entity].routes.ts`, `routes/index.ts` — input validation, controller logic.
   - Services: `src/services/[entity].service.ts`, `src/shared/errors.ts` — external API calls wrapped with timeouts/retries.
   - Views: `src/views/[entity]/`, shared layout/partials, client-side scripts if any.
   - Styles: `_custom.scss`, `app.scss`.
   - Binding refs (read on demand, not auto-imported): `design-system.md`, `layout.md` — for design-system/layout deviations.

4. **Trace the flow** following the request path: view (form/fetch call) → route (input validation, `src/routes/`) → service (`src/services/`, external API call via `fetch`) → response shaped back to the view. For errors: service throws → route catches and returns an error payload → view toasts. For theming: accent → `_custom.scss` (`$primary`) → Bootstrap-compiled `--bs-*` in `app.scss`. Cross-reference every endpoint against the endpoints table in `docs/specs/04-architect.md`.

5. **Report** (in the user's language):
   - What the code does (behavior).
   - How it connects across layers (dependencies, data flow, API endpoints called).
   - Any inconsistency vs the contract or the rules (`rules/*`), with the rule named — including security (`@rules/security.md`).
   - `file:line` references.
   - **Flag any unverified assumption explicitly** — do not fabricate a runtime behavior you could not read.

## When to ask the user

Use `AskUserQuestion` when:
- **Multiple valid scopes** — "analyze the settings page" could mean the view, the route, the config service, or all.
- **Multiple readings** — "how does saving work" — which entity? the request round-trip? the external API call? the validation?
- **Depth vs breadth** — a deep audit of one entity vs a survey of several.
- **Output format** — short summary, structured report, or actionable findings list.

Offer 2–4 concrete options, recommended one first. Do not ask when the scope is obvious or you are just confirming a fact.

## Anti-patterns — what NOT to do
- **Do not** modify code during an analysis. This skill is read-only; if a fix is wanted, hand off to `/local-webapp-fix-issue` or `/local-webapp-add-feature`.
- **Do not** report a behavior you inferred but did not read — mark it as an assumption and offer to verify.
- **Do not** describe the layers in the abstract — anchor every claim to a `file:line`.
- **Do not** silently pick one interpretation when several exist — ask.

## When the user asks something adjacent
- **"And fix it"** → switch to `/local-webapp-fix-issue` (bug) or `/local-webapp-add-feature` (change), carrying the analysis findings.
- **"Is this secure / well-architected?"** → compare against `@rules/security.md`, `docs/specs/04-architect.md`, and `@rules/mvc.md`; report deviations, do not refactor (that is `/local-webapp-refactor-code`, on request).
