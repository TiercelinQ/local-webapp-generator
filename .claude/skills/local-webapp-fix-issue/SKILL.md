# /local-webapp-fix-issue — Fix a bug (root cause)

## Role
Debugger — find the root cause and fix it cleanly, never paper over it.

## Goal
Resolve the failure so the relevant `@rules/verification.md` checks pass, with the minimum correct change.

## Deliverable
The corrected file(s) on disk + a passing verification + (after a multi-attempt anomaly) a cleanup report.

---

> If the project root has not been provided in this flow, first ask: `Project root? (folder path)`.

## Decision tree — classify the failure first

Read the actual error before touching code. Classify, then act in this order:

### 1. Typecheck / lint error (`npm run typecheck`, `npm run lint`)
- Read the exact message + `file:line`. Most are precise (type mismatch, missing import, unused symbol, `any`).
- Fix the cause. **Do not** add `// eslint-disable` or `as any` to silence it unless genuinely wrong and justified in a comment.

### 2. Build failure (`npm run dev` / `npm run build`)
- `tsc` error surfacing at build → trace to the declaration.
- Missing/misconfigured dependency, import path error, or a `tsconfig.json` mismatch → check `@rules/config.md`.
- Port already in use on `npm run dev` → check `.env` `PORT`, or another instance still running.

### 3. Runtime exception
- Caught by the global `uncaughtException`/`unhandledRejection` handler (`@rules/errors.md`)? Identify the service/route that raised it. Data shape or validation issue → route input validation; external call failure → service (`@rules/api-calls.md`).
- Unhandled in a route handler → missing `try/catch` or missing `next(err)` in an async handler; fix at the layer that owns the cause, not where the symptom surfaces.

### 4. Route / service error (call does nothing / 404 / unexpected response shape)
- Trace the path **end-to-end**: route registration ↔ route handler ↔ service function ↔ external endpoint (if any) ↔ view/response shape. A mismatch in any link breaks it. Fix the broken link, keep the chain consistent.

### 5. Security gap (`@rules/security.md`)
- Unvalidated route input, a secret hardcoded or logged instead of read from `.env` via `config.ts`, missing timeout/retry on an outbound call, a response leaking internal error detail to the client. These are never "acceptable for now" — fix to the rule.

### 6. CSS / design deviation (visual bug)
- Hardcoded color/size duplicating an available Bootstrap variable/utility, inline `style=""`, missing `data-bs-theme` handling, a custom-built component reinventing a native Bootstrap one (`.btn`/`.modal`/`.toast`/`.navbar`/`.offcanvas`), a blocking `alert()`/`confirm()`. Route the value through `_custom.scss`/Bootstrap utility classes, or replace the native dialog with the Bootstrap modal/toast. See `@rules/css.md` / `@rules/errors.md`.

## Steps

Read `design-system.md` / `layout.md` on demand if the fix touches UI (no longer auto-imported).

1. Get the real error (command output, stack trace, server log, or the user's repro). If you cannot reproduce, ask for the exact message — do not guess.
2. Classify with the tree above; read both the failing site and the declaration it depends on.
3. **Ask: "knowing what I know now, what is the clean fix?"** Implement that, not the quickest patch. If the clean fix is larger than expected, say so before applying.
4. Apply the minimum correct change. Respect the layers, the contract (`docs/specs/04-architect.md`), and the security rules.
5. **Verify**: re-run `@rules/verification.md §A` for the affected area; confirm the targeted failure is gone and nothing else broke. Then apply `@rules/readme.md` — if the fix changed a README-documented aspect (dependency, structure, config key), regenerate the README.
6. **Changelog**: append a `### Fixed` entry under `## [Unreleased]` in `docs/release/CHANGELOG.md` (`@rules/versioning.md`) — in English, one concise line, no version bump (the bump happens at `/local-webapp-release`). If the file is absent (legacy app), skip silently and suggest `/local-webapp-load-project` to initialize it. Skip for a non-code fix with no user-visible effect (e.g. a doc typo).
7. If it took several attempts: produce the **cleanup report** (`@rules/mvc.md` — list every dead element added during failed attempts), then offer `Do you want to remember this point? /local-webapp-save-memory`.

## Anti-patterns — what NOT to do
- **Do not** silence a typecheck/lint finding with `as any` / `// eslint-disable` instead of fixing the cause.
- **Do not** weaken input validation or security headers to make an error disappear — fix the actual cause within `@rules/security.md`.
- **Do not** wrap a bug in a `try/catch {}` that hides it.
- **Do not** hardcode a value to "make it look right" — fix it through the tokens.
- **Do not** patch only one link of a broken route/service chain and leave it inconsistent.
- **Do not** leave failed-attempt residue in the file. Clean it up.
- **Do not** expand the fix into an unrequested refactor; flag genuinely-wrong surrounding code for `/local-webapp-refactor-code`.
- **Do not** claim it is fixed without re-running the verification (or telling the user which command to run if no env).

## When the user asks something adjacent
- **"Just make the error go away"** → the error is a symptom; explain you are fixing the cause. A genuine temporary silence is explicit and flagged as debt.
- **"It's slow"** → not a crash; optimization (caching, redundant calls, large payloads) — handle as a finalization or `/local-webapp-refactor-code` item, on request.
